Enhance the existing Tazq Project Management module by adding a new first-class tab called "Planning".

IMPORTANT:
Do not redesign or break the existing Tazq project, task, feature, defect, test case, workspace or finance functionality.

Planning must become the place where a Project Manager defines, develops, reviews and continuously updates the project plan.

Planning must support BOTH:
1. Manual planning
2. AI-assisted planning

The architecture must be AI-ready and methodology-driven.

============================================================
1. PURPOSE OF PLANNING
============================================================

Planning is NOT a dashboard.

Planning is the PM's working area for defining how a project will be delivered.

The PM should be able to:

- Define project phases
- Define stages
- Define milestones
- Define feature groups
- Define features
- Define user stories
- Define dependencies
- Define planned dates
- Define estimated effort
- Define resources
- Review the complete project plan
- Modify the plan at any time
- Ask AI to create or elaborate planning at any selected level
- Export the resulting project plan as PDF

Planning must support progressive elaboration.

The PM does NOT have to fully plan the project at once.

============================================================
2. PROJECT STRUCTURE
============================================================

Planning must support the following logical structure:

Project

Optional Phase

Optional Stage

Milestone

Feature Group (optional)

Feature

User Story

Task

Test Case

Defect

IMPORTANT:

Do NOT make this a rigid mandatory hierarchy.

A project may have:

Project → Features → Tasks

or:

Project → Phase → Milestone → Feature → User Story → Task

or any appropriate combination.

Phase is OPTIONAL.

Stage is OPTIONAL.

Feature Group is OPTIONAL.

User Story is OPTIONAL.

The system must support unassigned items where appropriate.

Do not automatically create "Phase 1", "Stage 1", etc.

============================================================

============================================================
5. PLANNING IS EDITABLE
============================================================

Every planning item must be editable.

The PM should be able to:

- Add
- Edit
- Delete
- Move
- Reorder
- Duplicate
- Change dates
- Change dependencies
- Change owner
- Change estimated effort
- Change status

Changes must immediately update the project plan.

Planning is never locked after AI generation.

The PM remains the final authority.

============================================================
6. DATE MANAGEMENT
============================================================

Dates are important but NOT mandatory.

Every planning entity should support:

- Planned Start Date
- Planned End Date
- Duration

Dates may be empty.

If dates are provided, validate:

Start Date <= End Date

If a child item has dates outside its parent's date range, warn the PM.

Example:

Feature dates should normally fall within the relevant milestone/phase dates.

Do not prevent the PM from overriding this.

Use warnings rather than hard blocking wherever practical.

============================================================
7. DATE PROPAGATION
============================================================

Provide intelligent date calculation.

Example:

If a Feature has:

Start: 10 Aug
End: 15 Aug

and its User Stories have dates,

the Feature dates can be calculated from the earliest and latest child dates.

Allow the PM to choose:

Manual Dates
or
Calculated From Children

Do not silently overwrite manually entered dates.

============================================================
8. DEPENDENCIES
============================================================

Planning items should support dependencies.

Examples:

Feature B depends on Feature A.

Milestone 2 depends on Milestone 1.

User Story B depends on User Story A.

Support dependency types initially:

- Finish to Start
- Start to Start

The architecture should allow additional dependency types later.

Display dependency warnings when dates conflict.

============================================================
9. PLANNING METHODOLOGY
============================================================

Planning must always know how effort estimation is being performed.

Add:

Planning Methodology

as a project-level planning setting.

Initial options:

- Manual
- Complexity Based
- Component Based
- Function Point Analysis
- Story Point Based
- Historical Data Based
- Custom

Do not fully implement every methodology now.

Implement the methodology framework and Manual methodology first.

The architecture must allow future methodologies to be added independently without changing the Project module.

============================================================
10. METHODOLOGY PLUGIN ARCHITECTURE
============================================================

Create a generic Planning Methodology interface/service.

Conceptually:

PlanningMethodology

- getMetadata()
- getInputSchema()
- validateInput()
- calculateEffort()
- calculateDuration()
- calculateCost()
- explainCalculation()

Each methodology must be independently implementable.

Example future services:

ManualMethodology
ComplexityMethodology
ComponentMethodology
FunctionPointMethodology
StoryPointMethodology

The Project Planning module must not contain methodology-specific calculation logic.

============================================================
11. CALCULATION TRANSPARENCY
============================================================

Every calculated effort value must be explainable.

The PM should be able to click:

"How was this calculated?"

Example:

Planning Methodology:
Component Based

UI:
Medium = 16 hours

Business Logic:
Complex = 32 hours

Backend:
Medium = 20 hours

Testing:
12 hours

Total:
80 hours

Do not present AI-generated estimates as unexplained numbers.

Add an "AI Plan" action.

Plan Project

Existing Features

============================================================
15. AI GENERATION RULE
============================================================

AI must NOT directly create production records.

AI first produces a proposal.

Example:

AI Planning Proposal

3 Features
11 User Stories
24 Acceptance Criteria
18 Suggested Tasks

Show the proposal to the PM.

Actions:

Accept All
Accept Selected
Edit
Reject

Only approved items become actual Tazq records.

============================================================
16. AI MUST RESPECT EXISTING PLANNING
============================================================

If a Feature already has User Stories, AI must not recreate them blindly.

AI should inspect existing records and propose only missing or improved items.

Example:

Existing:

Feature:
Leave Application

Existing Stories:
US-001
US-002

AI should say:

"I found 2 existing User Stories and identified 3 additional Stories."

The PM decides what to add.

Avoid duplicate records.

============================================================
17. AI AND METHODOLOGY SEPARATION
============================================================

IMPORTANT ARCHITECTURAL RULE:

AI understands and decomposes requirements.

The Planning Methodology calculates effort.

AI must NOT independently invent final effort calculations when a methodology is selected.

Example:

Project methodology:
Component Based

AI determines:

UI = Medium
Backend = Complex
Business = Medium

The Component Methodology calculates:

UI = 16h
Backend = 40h
Business = 24h

Total = 80h

This separation must be maintained.

============================================================
18. PLANNING COVERAGE
============================================================

Introduce a metric called:

Planning Coverage

This represents how much of the project has been elaborated.

It is NOT project completion.

Example:

Project:

5 Milestones

2 Fully Planned
1 Partially Planned
2 High-Level Only

Display:

Planning Coverage: 62%

Clearly label this separately from:

Execution Progress

Never represent Planning Coverage as project completion.

============================================================
31. IMPORTANT PRODUCT PRINCIPLES
============================================================

1. Planning is optional in depth but always available.

2. Phase is optional.

3. Stage is optional.

4. Feature Group is optional.

5. Dates are optional.

6. Manual planning must work completely without AI.

7. AI assists; PM approves.

8. AI must not duplicate existing planning.

9. Planning methodology determines how effort is calculated.

10. AI feeds inputs into the methodology; AI does not replace the methodology.

11. Every calculated estimate must be explainable.

12. Planning Coverage must never be confused with Execution Progress.

13. Planning can be performed progressively at any level.

14. Planning methodology must be pluggable so new methodologies can be added independently.

15. Planning must eventually produce a professional project plan PDF.

Before coding, inspect the existing Tazq Project Management database schema, APIs, UI components and existing Feature, Feature Group, Milestone, Task, User Story, Test Case and Defect implementations.
